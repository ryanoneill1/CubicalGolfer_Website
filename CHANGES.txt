WHAT IT DOES
--------------------------------------------------------------------------
Every outbound Amazon link now carries the tracking ID of the PAGE it sits
on, so Associates will report earnings per page group instead of one
site-wide number.

--------------------------------------------------------------------------
WHY IT IS A POST-BUILD REWRITE, NOT 263 URL EDITS
--------------------------------------------------------------------------
I started down the obvious path and abandoned it. The tag is hardcoded 263
times inside affiliate-links.ts, and editing those would tag the PRODUCT —
which tells you nothing you cannot already get from the Associates product
report. Worse, a registry entry is shared across pages: garmin-approach-r10
sits on your launch-monitor roundups AND on /shaft-flex-guide/.

Threading the page slug through 25+ components was the other option. The
failure mode there is silent — miss one component and those links quietly
never appear in the split, and nothing tells you.

So the new step rewrites the tag in the built HTML, keyed off the page's own
file path. No render site can be missed, because it operates on the final
output rather than the code that produced it. The page path IS the group,
which is exactly the question you are asking.

  scripts/apply-tracking-ids.ts   new, runs immediately after `astro build`
  package.json                    one insertion into the build chain

SAFE BY CONSTRUCTION. It only ever swaps cubicalgolfer-20 for another ID in
your own account. An unclassified page falls to `misc`. A link it never
touches keeps the default tag. Worst case is an unattributed commission,
never a lost one — and it FAILS the build if an Amazon product link carries
no tag at all, which would be a real loss.

--------------------------------------------------------------------------
TWO VALIDATORS WIDENED — read this, it is the one thing I changed in your
safety net
--------------------------------------------------------------------------
Two validators read the built HTML and looked for the literal string
`tag=cubicalgolfer-20`. With eight IDs in play they would have failed on
every page, so both now match the tag FAMILY:

  scripts/validate-disclosure-position.ts     tag=cubicalgolfer-20
  scripts/validate-astro-affiliate-links.ts     -> tag=cubicalgolfer(?:-[a-z]+)?-20

The intent of both checks is unchanged: "this link is monetised." They still
reject an untagged link, a foreign tag, or a tag belonging to anyone else.
I widened them rather than removed them, and I am flagging it because
loosening a check to make my own change pass is exactly the move that should
be looked at twice.

Nothing else in the 100 pre-existing validators was touched.

--------------------------------------------------------------------------
HOW PAGES ARE GROUPED, AND THE TWO JUDGEMENT CALLS IN IT
--------------------------------------------------------------------------
Rules are tested in order; first match wins. Both calls below are in the
script's comments so the next person reading it knows they were decisions,
not accidents.

1. `gift` is tested FIRST, so /black-friday-golf-launch-monitor-deals/
   reports as a GIFT page, not a launch-monitor one. It could defensibly go
   either way. I chose gift because the question Q4 has to answer is "did
   the seasonal bet earn anything", and splitting the deal pages across
   groups makes that unreadable. Say the word and I will flip it.

2. `tool` is deliberately narrow — calculators, planners, budget tools and
   hub pages only. Charts and finders fall through to their subject, so the
   compression chart reports as a BALL page, which is what it is.

`misc` holds 66 pages: accessories, push carts, umbrellas, towels, swing
analysers, alignment sticks, and the pages with no affiliate links at all
(/about/, /404/). That is a real bucket, not a dumping ground — but if any
of it turns out to earn, it is worth splitting out later.
