WHY NOT [...slug].astro, THE "WORST" FILE
It has 88 inline styles — the most left — but 73 of its 79 distinct strings
are used EXACTLY ONCE. Extracting repeated strings would have yielded 15 of
88, by turning one-offs into one-off classes, on the template that renders 215
pages. Ranking the whole codebase by CONVERTIBLE attributes instead of raw
count puts it 12th, not 1st. So it was skipped, and the measurement turned up
something much bigger.

THE REAL FINDING
Only 36% of the remaining 1,239 inline styles sit in repeated strings, so the
extract-to-classes technique caps out around 446 and cannot finish F9. Asking
what the other 793 actually CONTAIN:

    402   off-grid margin/padding values   <- invisible to every check
    200   raw hex colours bypassing the colour tokens (incl. #1E3A28 = --green)
    573   hardcoded font-sizes
      2   raw border-radius, 0 raw box-shadow   <- these are genuinely clean

Sprint 182 taught validate-spacing-scale to read component <style> blocks and
found 73 off-grid values. The inline attributes were still invisible, and that

18px x55. Five and a half times what Sprint 182 fixed.

      article-body HTML), with its OWN ceiling, separate from the CSS one.

ONE THING I GOT WRONG, AND THE NOTE IT LEFT BEHIND
Mid-sprint I concluded the new page styles were not being applied, because
grepping dist/_astro/*.css for the rule found nothing while the elements
carried their data-astro-cid-* attribute. That was wrong. Astro's
build.inlineStylesheets default is 'auto', so a small page <style> block is
INLINED into the page <head> instead of written to a .css file. I had moved the
block and written a comment asserting Astro "emits no stylesheet at all";
I then tested both positions, found they behave identically, and rewrote the
comment to say what is actually true. A false note in the code is worse than
no note. The rules are confirmed present in the built HTML, correctly scoped,
on 5 sections and 7 headings.
