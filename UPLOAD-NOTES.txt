── 1. THE CHEAT SHEET PDF WAS GENUINELY CORRUPT ──────────────────────────────
Not a viewer problem. Reproduced it here and it is a renderer bug I should
have caught when I built that PDF spec.

The table renderer advanced every row by a FIXED 16pt regardless of what was
in it. The "Balls on our chart" cell lists every ball in a compression band —
300+ characters — which wrapped to six lines and then had the next row drawn
straight over the top of it, bleeding into the second table's header.

Two fixes, because there were two problems:

  RENDERER  Every cell is now measured with heightOfString and the row takes
            the tallest. Page breaks also use the real height, so a tall row
            can no longer be half-drawn at the bottom of a page. This fixes
            the whole class, not this instance — it protects all NINE PDFs.

  CONTENT   A cheat sheet is a glance, not an index. Listing all 16 balls in
            the mid band pushed it to two pages and duplicated the full table
            sitting right below it. Each band now reads "16 balls — <four
            examples>, +12 more below".

Back to ONE page, readable, nothing overlapping. I re-rendered all nine PDFs
and checked the club distance chart too, to be sure the renderer change did
not disturb the ones that were already fine. It did not.

── 2. THE CHART IMAGE: WRONG PLACE, WRONG SIZE ───────────────────────────────
You are right on both counts and the second one is the worse mistake.

Placement: I put it directly under the H1, which made a STATIC picture the
first thing on the page — standing in front of the actual interactive tool.
That is backwards. It now sits immediately after "In this guide", exactly
where you said.

Size: it is a 1200px image and I set width:100%. In a 1400px container the
browser UPSCALES it, so the type was bigger than the page's own headings.
Capped at 880px.

It is still not interactive, and it is not meant to be — it exists because
three competitors hold the image pack above every organic result on our
biggest query and a sortable HTML table gives Google nothing to put there.
But it should support the tool, not block it. Moving it does that.

Side effect worth knowing: it is now on the light body rather than the dark
hero, so the caption goes back to ordinary body colours. The contrast fix
from Sprint 136 is no longer needed there, which is a cleaner outcome than
the hard-coded value I shipped yesterday.
